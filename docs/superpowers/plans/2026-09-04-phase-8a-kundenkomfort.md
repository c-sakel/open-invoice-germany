# Phase 8a — Kundenkomfort Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Kundenspezifische Vorgaben (§28) mit Konsum bei Beleganlage, CRUD für mehrere Adressen (§29) und Ansprechpartner (§30) mit Snapshots und Platzhaltern, benutzerdefinierte Kundenfelder (§31), „Letztes Dokument übernehmen" (§32).

**Architecture:** Kundendomain unter `src/domain/customer/` (addresses, contacts, custom-fields, defaults); Snapshot-Erweiterung in `src/domain/snapshot.ts` (Adresse aus Auswahl, Ansprechpartner, Custom Fields); Vorlagenkontext liest Snapshots; Take-over als reines Prefill ohne Schreibzugriff; UI: Kundenseite mit Tabs, Selektoren in allen Belegformularen, Prompt beim Kundenwechsel; Routen + MCP spiegeln die Domain.

**Tech Stack:** Next.js 16, Prisma 6 (SQLite+Postgres), Zod 4, vitest.

**Spec:** docs/superpowers/specs/2026-09-04-phase-8a-kundenkomfort-design.md (specs); Ist-Stand phase-8-ist-stand.md.

## Global Constraints
- GoBD/Snapshots: Belege speichern Adresse (gewählte Rechnungs-/Lieferadresse), Ansprechpartner (`contactSnapshotJson`), Custom-Field-Werte (`buyerSnapshotJson.customFields`) und Bestellreferenz bei Anlage; Festschreibung friert (bestehender Mechanismus, `snapshotSource`). Kundenstamm-Änderungen wirken nie auf bestehende Belege. Kunden-CRUD ohne ChangeLog.
- Prioritätskette je Vorgabe: explizite Eingabe > Kunde > Zahlungsmethode (nur Frist) > DocumentSettings > Systemdefault. Nie explizite Nutzereingaben überschreiben.
- Zod an jeder Boundary; Routen/MCP/Formulare nutzen dieselben Domain-Funktionen; alle Abfragen org-scoped (Adressen/Kontakte über `customer.orgId`).
- Geld Integer-Cent; Custom-Field NUMBER als Dezimal-String (max. 4 Nachkommastellen), keine Float-Rechnung.
- Migrationen SQLite UND Postgres (Schemadateien identisch bis auf provider; Postgres via migrate diff); Tabellen danach 36 (CustomFieldDefinition). Relationen `onDelete: SetNull` für Adress-/Kontakt-FKs (bereits so).
- E-Rechnung: `orderNumber` (BT-13) existiert seit 4b — Kundenvorgabe `orderReference` belegt es vor; XML-Mapping unverändert; `validate:erechnung` grün.
- Bestehende Selektoren (Rechnungsformular: Rechnungsadresse, Ansprechpartner) bleiben; Angebot/AB bekommen dieselben; Lieferschein bekommt `shippingAddressId` + `contactPersonId` (neue Spalten, SetNull).
- Testjahre: 2059 customer-domain, 2060 consumption/take-over, 2061 routes, 2062 mcp (vorher `grep -r "20(59|6[0-2])-" test/`).
- Prüfkette im Vordergrund vor jedem Commit-Abschluss: typecheck, lint, test, build, validate:erechnung; Task 4 zusätzlich Postgres-Skript.

### Task 1: Schema, Migrationen, Zod, Kundendomain (Adressen, Ansprechpartner, Custom Fields, Vorgaben)
**Files:** Modify `prisma/schema.prisma` + `prisma/schema.postgres.prisma`, `src/schemas/index.ts` (oder neu `src/schemas/customer.ts`); Create `src/domain/customer/addresses.ts`, `contacts.ts`, `custom-fields.ts`, `defaults.ts`, Migration `phase8a_customer` (beide DBs); Tests `test/unit/customer-schemas.test.ts`, `test/integration/customer-domain.test.ts` (2059).
**Schema (exakt):** Customer += `defaultCurrency String?`, `defaultDiscountPermille Int @default(0)`, `invoiceEmail String?`, `invoiceCc String?`, `quoteEmail String?`, `eInvoicePreferred Boolean @default(false)`, `orderReference String?`, `deliveryTermsText String?`, `paymentTermsText String?`, `language String @default("de")`, `customFieldsJson String?`. Neu `CustomFieldDefinition { id, orgId, org, key String, label String, type String, optionsJson String?, required Boolean @default(false), sortOrder Int @default(0), isActive Boolean @default(true), createdAt, updatedAt, @@unique([orgId, key]), @@index([orgId]) }`. DeliveryNote += `shippingAddressId String?` (+ Relation "DeliveryNoteShippingAddress", SetNull), `contactPersonId String?` (SetNull), `contactSnapshotJson String?`; Invoice/Quote += `contactSnapshotJson String?`. CustomerAddress/ContactPerson: Relationen zu DeliveryNote ergänzen.
**Zod:** `customerAddressInputSchema` {type BILLING|SHIPPING|OTHER, label ≤60, addressLine1 1..120, addressLine2 ≤120, postalCode 1..12, city 1..80, countryCode 2 Großbuchstaben default DE, isDefault}; `contactPersonInputSchema` {firstName 1..60, lastName 1..60, role ≤60, phone/mobile ≤40, email z.email() optional, isDefault}; `customFieldDefinitionInputSchema` {key `^[a-z][a-z0-9_]{1,39}$`, label 1..60, type enum, options string[] (1..50, nur SELECT), required, sortOrder, isActive}; `customFieldValuesSchema(definitions)` = Funktion, die ein Zod-Objekt erzeugt (TEXT ≤500, NUMBER `^-?\d+(\.\d{1,4})?$`, DATE ISO `YYYY-MM-DD`, BOOLEAN, SELECT in options; required prüfen; unbekannte Keys → Fehler); `customerDefaultsInputSchema` (die 10 Felder; invoiceCc: kommagetrennte E-Mails ≤5; currency 3 Großbuchstaben; discount 0..1000; language `^[a-z]{2}$`).
**Domain:** addresses: `listAddresses(orgId, customerId)`, `createAddress`, `updateAddress`, `deleteAddress` (FKs SetNull; kein Snapshot-Effekt), `setDefaultAddress(orgId, customerId, id)` (nur ein Default je Typ, Tx), `defaultAddressFor(orgId, customerId, type)`; contacts analog inkl. `setDefaultContact`; custom-fields: `listCustomFieldDefinitions(orgId, {activeOnly})`, `upsertCustomFieldDefinition`, `deleteCustomFieldDefinition` (Werte bleiben), `reorderCustomFields`, `parseCustomerCustomFields(orgId, json)` (validiert gegen Definitionen, liefert Objekt), `setCustomerCustomFields(orgId, customerId, raw)`; defaults: `saveCustomerDefaults(orgId, customerId, raw)`, `customerDefaultsFor(orgId, customerId)` → typisiertes Objekt inkl. defaultBillingAddress/defaultShippingAddress/defaultContact.
**Tests:** je Schema Grenzen; Default-Wechsel setzt alten Default zurück; Löschen einer referenzierten Adresse → Beleg-FK null, Snapshot unverändert; Custom-Field-Validierung je Typ inkl. required/unknown key; SELECT-Optionen; Schemadateien identisch.
