# Phase 8b — Workflow und UX: Status, Filter, Schnellaktionen, Zahlungsdialog, Wiederkehrend, Timeline, Dashboard, Kundendetailseite, Benachrichtigungen, Navigation

**Lastenheft:** §39–§49, §56, §57; §58 Phase 8 (zweite Hälfte) und Teile von Phase 9 (Benachrichtigungen). Bindend §50–§55, §59.
**Ist-Stand:** `phase-8-ist-stand.md`. Kurz: Duplizieren (§47) und interne Notizen (§48) sind fertig; Zahlung erfassen (§42) und wiederkehrende Rechnungen (§43) weitgehend; kein dynamischer Rechnungsstatus fällig/überfällig, keine Listenfilter/Suche, keine Zeilenaktionen in Listen, kein ActivityLog, keine Timeline, kein Dashboard (Startseite ist Marketing), Kundenseite nur Formular, keine In-App-Benachrichtigungen, Navigation flach.

## 1. Entscheidungen

| Bereich | Entscheidung |
|---|---|
| §39 Status | `effectiveInvoiceStatus(inv, now)` rein in `src/domain/invoice/status.ts`: DRAFT → „Entwurf"; CANCELLED → „storniert"; PAID → „bezahlt"; sonst: PARTIALLY_PAID → „teilbezahlt"; FINALIZED/SENT mit dueDate < heute → „überfällig"; dueDate = heute → „fällig"; sonst „offen" (SENT) / „festgeschrieben" (FINALIZED, noch nicht versendet). Nichts wird gespeichert. `StatusBadge` bekommt DUE/OVERDUE; Listen/Detail/Filter nutzen ausschließlich diese Funktion. |
| §40 Filter | Rechnungsliste: Query-Parameter `status` (all/draft/open/due/overdue/partial/paid/cancelled), `customerId`, `from`/`to` (issueDate), `minCents`/`maxCents` (gross), `number`, `paymentMethodId`, `eInvoice` (hasXml? Ruling: Kunde eInvoicePreferred ODER Leitweg-ID vorhanden), `currency`, `q` (Volltext über number, Kundenname, orderNumber, Positionstexte via `contains`, DB-portabel, kein FTS-Index). Domain `listInvoices(orgId, filter, {limit, offset, sort})` mit Zod-Filterschema; Status fällig/überfällig serverseitig über dueDate-Vergleich + paid-Status. Gleiches Muster (reduziert: status, customer, from/to, q) für Angebote/AB (`/dokumente`), Lieferscheine, Abos. UI: Filterleiste + Suchfeld, Paginierung 50/Seite, URL-getragen. |
| §41 Schnellaktionen | `RowActionsMenu` (Drei-Punkte) je Zeile in Rechnungs-, Angebots-/AB-, Lieferschein-Liste; Einträge status-gated über eine reine Funktion `availableActions(doc)` (dieselbe Logik wie Detailseite, dort ebenfalls verwendet — keine Doppelung): öffnen, bearbeiten (DRAFT), duplizieren, PDF, XRechnung (Rechnung, nicht Entwurf), per E-Mail senden, erneut senden (bereits versendet), Zahlung erfassen (offen), Zahlungserinnerung/nächste Mahnung (überfällig, Prozess aktiv), Lieferschein erstellen (AB/Angebot angenommen), stornieren (festgeschrieben). Aktionen rufen die bestehenden Routen/Dialoge; keine neuen Backends außer `availableActions`. |
| §42 Zahlungsdialog | `Payment.note String?` neu; `PaymentForm`: Referenz-Feld sichtbar, Notiz, Button „Restbetrag übernehmen" (setzt Betrag = offener Betrag), Skonto-Vorschau bleibt; Zahlungshistorie bleibt. Route/Zod/MCP (`record_payment`) um `note` erweitert. |
| §43 Wiederkehrend | `RecurringInvoice` += `maxRuns Int?`, `emailTemplateId String?`, `showPeriodText Boolean @default(true)` (überstimmt Settings-Default je Abo), Intervall „benutzerdefiniert" = `intervalUnit DAY` mit `intervalCount` (Zod-Enum + DAY); Ende bei `issuedCount >= maxRuns` → ENDED; Historie existiert. UI-Felder ergänzen. |
| §44 Timeline | Neues Modell `ActivityLog { id, orgId, entityType, entityId, type, actor, at, dataJson String?, @@index([orgId, entityType, entityId, at]) }` OHNE Hash-Kette (Ruling CLAUDE.md). Schreiber `logActivity(tx|db, {...})` in: Belegerstellung, Bearbeitung (Entwurf), Festschreibung, Versand (EmailLog bleibt Quelle, zusätzlich Activity), Zahlung, Storno, Gutschrift, Mahnung erstellt/gesendet, Status-/Konvertierungsereignisse, Take-over/Duplizieren, Anhänge. Timeline-Domain `buildTimeline(orgId, {kind, id})` merged ActivityLog + EmailLog (zugestellt/bounced) + Payment + Dunning + berechnete Termine („Zahlungsziel erreicht" aus dueDate, „Angebot läuft ab" aus validUntil) chronologisch; Komponente `DocumentTimeline` auf allen Detailseiten. ChangeLog bleibt Audit (nicht im UI; Backlog: Audit-Ansicht). Backfill: keiner (Timeline beginnt mit Phase 8b; ältere Ereignisse aus EmailLog/Payment/Dunning erscheinen trotzdem). |
| §45 Dashboard | Route `/` wird nach Login das Dashboard (Marketing-Startseite entfällt für angemeldete Nutzer; unangemeldet bleibt Login). Domain `dashboardSummary(orgId, now)`: offene Forderungen, überfällig, heute fällig, diese Woche fällig, teilbezahlt, „Mahnungen erforderlich" (Kandidaten aus `runDunningJob`-Logik ohne Schreiben → gemeinsame Funktion `dunningCandidates`), Aging 0–7/8–30/31–60/61–90/>90 (Widerspruch zu §25 (1–7/…/>60) — Ruling: Dashboard nutzt die §45-Buckets, Mahnübersicht die §25-Buckets; gemeinsamer Helfer mit Bucket-Grenzen als Parameter), Umsatz laufender Monat, letzte 5 Belege, offene Angebote. Alles auf `openAmountCents`. |
| §46 Kundendetailseite | `/kunden/[id]` wird Detailseite mit Tabs Übersicht (KPIs: Gesamtumsatz = Σ brutto festgeschriebener Rechnungen abzgl. Gutschriften, offene/überfällige Forderungen, letzte Rechnung/Angebot) | Angebote | Aufträge | Lieferscheine | Rechnungen | Zahlungen | Mahnungen | Dokumente (Anhänge); die Phase-8a-Tabs (Stammdaten, Adressen, Ansprechpartner, Vorgaben, Kundenfelder) wandern unter „Bearbeiten" (`/kunden/[id]/bearbeiten`). Domain `customerOverview(orgId, customerId)`. |
| §49 Benachrichtigungen | Modell `Notification { id, orgId, type, title, body, link, entityType?, entityId?, createdAt, readAt?, dedupeKey String @unique }`, `NotificationSettings { orgId @unique, enabledTypesJson, emailDigest Boolean @default(false) }`. Typen: INVOICE_DUE_TODAY, INVOICE_OVERDUE, DUNNING_STAGE_REACHED, QUOTE_EXPIRING (≤3 Tage), RECURRING_FAILED, EMAIL_BOUNCED, EINVOICE_INVALID. Erzeugung: Scheduler-Job `notifications` (täglich, dedupeKey = type+entity+Datum) plus Ereignis-Hooks (bounce, recurring error, e-invoice validation failure beim Export/Versand). UI: Glocke im Header mit Ungelesen-Zähler, Liste `/benachrichtigungen`, „alle gelesen"; Einstellungen → Benachrichtigungen (Typen an/aus; E-Mail-Digest an Org-Owner täglich über Mailpipeline). MCP `list_notifications`, `mark_notifications_read`. |
| §56/§57 Navigation & UX | Header-Navigation gruppiert: Dashboard · Verkauf (Angebote, Auftragsbestätigungen, Lieferscheine, Rechnungen, Wiederkehrende Rechnungen, Gutschriften (= Rechnungsliste mit Filter type=CREDIT_NOTE), Mahnwesen) · Stammdaten (Kunden, Produkte) · Einstellungen (Tabs wie Phase 7). Mobile: Burger-Menü. Formulare: „Weitere Optionen" (Details-Element) für selten genutzte Felder (Bestellreferenz, Leitweg-ID, Lieferzeitraum, Druckoptionen, interne Notizen) in Rechnungs-/Angebotsformular. Dokumentvorschau: eingebettetes PDF (iframe auf bestehende PDF-Route) auf Detailseiten. |
| MCP (§55) | `list_invoices` mit Filterschema, `get_dashboard`, `get_customer_overview`, `get_timeline`, `list_notifications`, `mark_notifications_read`, `record_payment` (+note), `update_recurring_invoice` (neue Felder). |
| Nicht in 8b | Volltextindex; Mehrbenutzer-Benachrichtigungen (eine Org = ein Nutzer); Audit-Ansicht des ChangeLog (Backlog); Kanban/Drag&Drop. |
