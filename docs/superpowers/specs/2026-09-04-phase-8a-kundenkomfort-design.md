# Phase 8a — Kundenkomfort: Defaults, Adressen, Ansprechpartner, Custom Fields, Letztes Dokument übernehmen

**Lastenheft:** §28–§32 (P1 Kundenkomfort); §58 Phase 8 (aufgeteilt in 8a Kundenkomfort und 8b Workflow/UX: §39–49, 56, 57). Bindend §50–§55, §59.
**Ist-Stand:** `phase-8-ist-stand.md`. Kurz: `Customer` hat `defaultPaymentTermsDays` (ungenutzt — wird in Phase-7-Fix-Welle konsumiert), `defaultPaymentMethodId` (genutzt), `notes`, `leitwegId`, `peppolId`; `CustomerAddress` (BILLING/SHIPPING/OTHER, isDefault) und `ContactPerson` existieren als Modelle mit FKs auf Invoice/Quote und Selectoren im Rechnungsformular, aber **ohne CRUD** (keine Route, kein UI, kein MCP); Buyer-Snapshot vorhanden; Platzhalter `contact.name` aus Legacy-`contactName`; Custom Fields nur als Stub `customField: {}` im Vorlagenkontext; Duplizieren vollständig (`src/domain/document/duplicate.ts`).

## 1. Entscheidungen

| Frage | Entscheidung |
|---|---|
| §28 Customer-Felder | Neu: `defaultCurrency String?`, `defaultDiscountPermille Int @default(0)`, `invoiceEmail String?`, `invoiceCc String?` (kommagetrennt, Zod-validiert), `quoteEmail String?`, `eInvoicePreferred Boolean @default(false)`, `orderReference String?` (Bestellreferenz → BT-13), `deliveryTermsText String?`, `paymentTermsText String?`, `language String @default("de")` (nur gespeichert; PDFs deutsch → LIMITATIONEN). Bestehend bleiben `defaultPaymentTermsDays`, `defaultPaymentMethodId`, `notes` (= interne Notiz, UI-Label „Interne Notiz — nur intern sichtbar"), `leitwegId`. Bevorzugte Rechnungs-/Lieferadresse und Ansprechpartner = `isDefault` je Typ auf `CustomerAddress`/`ContactPerson` (kein zusätzliches Feld). |
| Konsum bei Anlage | Reihenfolge je Wert: explizite Eingabe > Kunde > Zahlungsmethode (nur Frist) > DocumentSettings > Systemdefault. Gilt für Rechnungs-, Angebots-, AB-, Lieferschein- und Konvertierungspfade sowie wiederkehrende Rechnungen bei Anlage. `defaultDiscountPermille` → `documentDiscountPermille` (nur wenn Beleg keinen eigenen Rabatt hat). `invoiceEmail`/`quoteEmail`/`invoiceCc` → Vorbelegung Empfänger/CC im SendEmailDialog (Fallback `customer.email`). `eInvoicePreferred` → Vorbelegung Standardanhänge XRechnung/ZUGFeRD zusätzlich zu `eInvoiceDefault`. `orderReference` → Beleg-Feld Bestellreferenz (existiert? sonst neu auf Invoice/Quote `buyerReference`/`orderReference`, XRechnung BT-13/BT-10 Mapping prüfen — Ruling: Feld `orderReference` auf Invoice/Quote, Mapping BT-13 `cbc:OrderReference/cbc:ID` bzw. CII `BuyerOrderReferencedDocument`, Fixture ergänzen). `deliveryTermsText`/`paymentTermsText` → Vorbelegung der Belegtexte vor den Dokumenttexten (TextTemplate). |
| §29 Adressen | CRUD-Domain `src/domain/customer/addresses.ts` (list/create/update/delete/setDefault je Typ; Löschen blockiert, wenn Beleg-FK referenziert → stattdessen `isActive=false`? Ruling: Löschen erlaubt, FKs auf Belegen bleiben (Snapshot ist maßgeblich), Prisma-Relation `onDelete: SetNull`), Routen `/api/customers/[id]/addresses[/[addressId]]`, UI-Tab im Kundenformular, Selector in allen Belegformularen (Rechnung hat ihn; Angebot/AB/Lieferschein nachziehen), Buyer-Snapshot nimmt die gewählte Adresse (bestehende Snapshot-Builder erweitern). MCP `list_customer_addresses`, `upsert_customer_address`, `delete_customer_address`. |
| §30 Ansprechpartner | analog `src/domain/customer/contacts.ts`, Routen `/api/customers/[id]/contacts[/[contactId]]`, UI-Tab, Selector in allen Belegformularen, Snapshot: `contactSnapshotJson` auf Invoice/Quote/DeliveryNote (Vor-/Nachname, Funktion, Telefon, Mobil, E-Mail) → Platzhalter `{{contact.firstName}}`, `{{contact.lastName}}`, `{{contact.email}}`, `{{contact.role}}`, `{{contact.phone}}`; `{{contact.name}}` = „Vorname Nachname" (Fallback Legacy `contactName`). E-Mail-Empfänger-Vorbelegung: Ansprechpartner-E-Mail > invoiceEmail/quoteEmail > customer.email. MCP `list_contact_persons`, `upsert_contact_person`, `delete_contact_person`. |
| §31 Custom Fields | `CustomFieldDefinition { id, orgId, key (slug, unique je Org), label, type TEXT|NUMBER|DATE|BOOLEAN|SELECT, optionsJson String? (SELECT), required Boolean @default(false), sortOrder Int, isActive Boolean @default(true) }`; Werte als `Customer.customFieldsJson String?` (Objekt key→Wert, Zod-validiert gegen Definitionen: NUMBER als Zahl (Integer/Dezimal als String? Ruling: Dezimal als String mit max. 4 Nachkommastellen, keine Float-Rechnung), DATE ISO-Datum, BOOLEAN, SELECT aus Optionen). Belege snapshotten die Werte in `buyerSnapshotJson.customFields` bei Anlage/Festschreibung → Platzhalter `{{customField.<key>}}` in E-Mail-/Dokumenttexten (Kontext aus Snapshot, Fallback Kunde). Einstellungen → Kundenfelder (CRUD, Reihenfolge, deaktivieren; Löschen nur ohne Werte? Ruling: Löschen entfernt Definition, Werte bleiben im JSON (harmlos) — LIMITATIONEN). Kundenformular rendert die Felder dynamisch. MCP `list_custom_fields`, `upsert_custom_field`, `set_customer_custom_fields`. |
| §32 Letztes Dokument übernehmen | Domain `src/domain/document/take-over.ts`: `findLastDocumentForCustomer(orgId, customerId, kind)` und `buildTakeOverPrefill(orgId, docId, { lines, texts, terms, prices })` → Prefill-Objekt für das Anlageformular (Positionen mit oder ohne Preise (ohne Preise = Preis 0, Nutzer ergänzt), Kopf-/Fußtext, Zahlungs-/Lieferbedingungen). Kein Beleg wird geschrieben (im Unterschied zu Duplizieren). UI: Beim Kundenwechsel im Anlageformular (Rechnung/Angebot/AB) und aktiver `DocumentSettings.offerLastDocument` erscheint „Letzte <Belegart> RE-… vom … übernehmen?" mit den vier Optionen; „Dokument duplizieren" als Alternative-Link. Route `GET /api/customers/[id]/last-document?kind=` und `POST /api/documents/[id]/take-over-prefill`. MCP `take_over_last_document` liefert das Prefill. |
| GoBD | Alle Kundenstamm-Änderungen wirken nie rückwirkend auf Belege (Snapshots inkl. Adresse, Ansprechpartner, Custom Fields, Bestellreferenz). Kunden-CRUD bleibt außerhalb des ChangeLog (Stammdaten). |
| Nicht in 8a | Sprache in PDF/Mail; Custom Fields auf Belegen/Produkten; Adress-Validierung; Dublettencheck. |
