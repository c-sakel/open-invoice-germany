# Phase 4 — Rechnungskomfort: Rabatte, Aufschläge, Skonto, Zahlungsmethoden, Editor, Positionsblöcke, Rich-Text, Anhänge

**Lastenheft:** §7 Rechnungseditor, §8 Positionsblöcke, §9 formatierte Positionstexte, §10 Gesamtrabatt/Aufschlag, §11 Skonto, §12 Zahlungsmethoden, §38 Dateianhänge; bindend §50 (Geld), §52 (E-Rechnung semantisch korrekt — Audit K1: Rabatt und AllowanceCharge-Mapping werden nie getrennt ausgeliefert), §54 (Tests für Rechen-/Steuerlogik).

**Baut auf:** Phase 1 (`PaymentMethod` mit UNTDID-4461-Code, `Customer.defaultPaymentMethodId`, `ContactPerson`, `CustomerAddress`), Phase 2 (Mailversand, Anhang-Builder), Phase 3a (Kopf-/Fußtexte, `headerText/footerText`, Kette).

## 1. Ist-Stand

- `InvoiceLine`: `discountPermille` (Prozentrabatt je Position) vorhanden; kein Festbetragsrabatt, keine Artikelnummer, keine Langbeschreibung, kein Positionstyp.
- Keine Belegrabatte/-aufschläge, kein Skonto-Modell (`paymentTerms` Freitext), kein Zahlungsmethoden-Bezug an der Rechnung (`PaymentMeansCode` hart „58"), `Payment.method` frei.
- `computeTaxBreakdown(lines)` (src/lib/tax.ts) summiert je Steuersatz aus `lineNetCents`; `TaxTotals { netTotalCents, taxTotalCents, grossTotalCents, breakdown[] }`. UBL schreibt `LineExtensionAmount = TaxExclusiveAmount = netTotalCents` (keine Allowance-Felder). `scripts/validate-erechnung.ts` validiert feste Beispielbelege — wird um Rabatt-/Skonto-Fixtures erweitert.
- `PaymentMethod` (Phase 1) hat bereits `description`, `paymentTermsDays`, `invoiceText`, `bankAccountRef`, `untdidCode`; `Payment.isSkonto` existiert — beides ohne UI/Verwendung.
- E-Rechnung: UBL (`xrechnung.ts`) und CII (`cii.ts`) ohne `AllowanceCharge`; Validatoren (KoSIT/Mustang) sind CI-Gate.
- Editor `NewInvoiceForm` (218 Zeilen): Kunde, Schema, Datumsfelder, Notizen, Zahlungsbedingungen-Text, Positionen flach.
- Anhänge: `EmailLog.attachmentsJson` nur Hashes; keine Dateiablage.

## 2. Entscheidungen

| Frage | Entscheidung | Warum |
|---|---|---|
| Umfang | **Zwei Pläne**: 4a Rechenwerk (Positions-/Belegrabatt, Aufschlag, Skonto, Zahlungsmethoden, E-Rechnung); 4b Editor (Kopfdaten, Positionsblöcke, Rich-Text, Drag&Drop, Produkt inline, Anhänge). Eine Spec. | 4a ist Steuer-/E-Rechnungs-kritisch und braucht ein eigenes Review; 4b ist UI-lastig. |
| Positionsrabatt | `discountPermille` bleibt; neu `discountCents Int @default(0)` (Festbetrag je Position, netto). Beide gleichzeitig erlaubt (erst Prozent, dann Festbetrag). `lineNetCents` = Menge×Preis − Rabatte, gerundet auf Cent (Milliunits: `round(quantityMilli × unitNetPriceCents / 1000)`). | §7 „Prozent, Festbetrag". |
| Belegrabatt/-aufschlag | Am Beleg (`Invoice`, `Quote`): `documentDiscountPermille`, `documentDiscountCents`, `documentChargePermille`, `documentChargeCents`, `documentChargeReason String?`. Berechnung: Nettosumme je Steuersatz S_r; Rabattbetrag D gesamt (Prozent auf Σ S_r oder Festbetrag); **proportionale Aufteilung** D_r = D × S_r / Σ S_r mit Largest-Remainder-Rundung, sodass Σ D_r = D exakt; Steuer je Satz auf (S_r − D_r + C_r). Reihenfolge: erst Rabatt, dann Aufschlag (auf die rabattierte Basis). | §10, Lastenheft-Beispiel 100 € 19 % + 100 € 7 %, 10 % → 10 € + 10 €. |
| Speicherung der Aufteilung | `taxBreakdownJson` erweitert um `allowanceCents`/`chargeCents` je Satz; Summen `netTotalCents` = Σ(S_r − D_r + C_r). Alte Belege ohne Felder bleiben gültig (Defaults 0). | Snapshot-Regel; PDF/XML lesen den Breakdown. |
| E-Rechnung Rabatt | Positionsrabatt → UBL `cac:AllowanceCharge` auf `InvoiceLine` (BG-27, `ChargeIndicator=false`, `Amount`, `BaseAmount`, `MultiplierFactorNumeric` bei Prozent) bzw. CII `ram:AppliedTradeAllowanceCharge`; `PriceAmount` bleibt der unrabattierte Einzelpreis, `LineExtensionAmount` = Netto nach Rabatt. Belegrabatt/-aufschlag → Dokumentebene BG-20/BG-21 **je Steuersatz** (eine AllowanceCharge pro Satz mit `TaxCategory`/`Percent`), `AllowanceTotalAmount`/`ChargeTotalAmount` (BT-107/108) in `LegalMonetaryTotal`; `TaxExclusiveAmount` = Σ Zeilen − Rabatt + Aufschlag. Reason-Code BT-98 „95" (Discount) / BT-105 Freitext. | §52; EN 16931 BR-CO-10/11/13; nur so bleibt der Validator grün. |
| Skonto-Modell | `Invoice`: `skonto1Permille Int?`, `skonto1Days Int?`, `skonto2Permille Int?`, `skonto2Days Int?`; `paymentTerms`-Freitext bleibt (wird aus Skonto + Zahlungsziel generiert, wenn leer). PDF-Ausgabe: „2 % Skonto bei Zahlung bis dd.MM.yyyy (Skontobetrag x,xx €), netto bis dd.MM.yyyy". | §11. |
| Skonto in E-Rechnung | XRechnung-Spezifikation: strukturierte Skonto-Angabe in BT-20 (`PaymentTerms/Note`) im Format `#SKONTO#TAGE=7#PROZENT=2.00#` (mehrere Zeilen für zwei Ziele, optional `#BASISBETRAG=`), gefolgt vom Klartext. CII: `ram:SpecifiedTradePaymentTerms/ram:Description` gleicher Text; Factur-X/ZUGFeRD EXTENDED kennt `ApplicableTradePaymentDiscountTerms` — Ruling: nur BT-20-Text (Profil EN 16931/COMFORT), Validator-Gate entscheidet. | §11 „soweit EN16931-konform". |
| Skonto bei Zahlung | `Payment.isSkonto` existiert seit Phase 1; neu `skontoForPaymentId String?` (Verweis auf die Zahlung, die den Skonto ausgelöst hat). `recordPayment` erkennt: Zahlung innerhalb Skontofrist und Betrag ≥ Brutto × (1 − p) − 1 Cent Toleranz → Vorschlag (UI/MCP-Parameter `applySkonto: true`) legt zweiten `Payment` mit `isSkonto`, Betrag = Restforderung, `method = "SKONTO"` (neuer Systemcode, UNTDID „ZZZ") an; Rechnung gilt als bezahlt. Kein automatisches Buchen ohne Bestätigung. ChangeLog `PAYMENT`/`SKONTO`. | §11 „erkennen/anbieten", GoBD: nachvollziehbar. |
| Zahlungsmethoden | `PaymentMethod` hat seit Phase 1 bereits `description`, `paymentTermsDays`, `invoiceText`, `bankAccountRef` (Freitext-Kontoreferenz), `untdidCode`, `isSystem`, `isActive`, `sortOrder` — **keine Schemaänderung**, nur `bankIban/bankBic/bankName String?` als optional abweichendes Konto ergänzen (Ruling: `bankAccountRef` bleibt als Anzeigetext). UI Einstellungen → Zahlungsmethoden (CRUD; Systemcodes nicht löschbar, Name/Text editierbar). `Invoice.paymentMethodId String?` + Snapshot der relevanten Felder in `paymentMethodSnapshotJson` beim Festschreiben (Phase-0-Muster). Vorbelegung aus `Customer.defaultPaymentMethodId`. `PaymentMeansCode` aus `untdidCode` (statt hart 58); bei abweichendem Konto dessen IBAN/BIC in `PayeeFinancialAccount`. `Payment.method` wird gegen `PaymentMethod.code` validiert (Phase 1). | §12; §52. |
| Zahlungsziel | `paymentTermDays` der Methode → Fälligkeitsdatum-Vorschlag (Kunde-Default `defaultPaymentTermsDays` hat Vorrang, dann Methode, dann 14). | §7 Zahlungsziel. |
| Kopfdaten Editor (4b) | `Invoice`: `subject String?`, `customerReference String?` (Bestand: `buyerReference` = BT-10, Mapper nimmt `invoice.buyerReference ?? customer.leitwegId`; neu `orderNumber String?` (BT-13), `internalReference String?`, `contactPersonId String?`, `billingAddressId String?`, `shippingAddressId String?`; Leitweg-ID kommt aus Kunde/Snapshot (Phase 0), am Beleg überschreibbar über `buyerReference`. | §7. |
| Positionsblöcke (4b) | `InvoiceLine`/`QuoteLine`: `lineType String @default("ITEM")` — `ITEM`, `HEADING`, `TEXT`, `SUBTOTAL`. HEADING/TEXT tragen nur `description`, keine Beträge (nicht in Summen, nicht im XML); SUBTOTAL wird beim Rendern berechnet (Summe der ITEMs seit letzter Überschrift/Zwischensumme), nicht gespeichert. E-Rechnung: nur ITEMs werden zu Zeilen; HEADING/TEXT gehen als `cbc:Note` der nächsten Position bzw. entfallen (Ruling: entfallen, Text nur PDF). | §8 „echte Section-Positionen". |
| Rich-Text (4b) | Speicherformat: **eingeschränktes Markdown** (fett `**`, kursiv `_`, unterstrichen `__`, Listen `- `/`1. `, Links `[t](https://…)`, Zeilenumbruch). Kein HTML gespeichert; Parser/Sanitizer eigen (`src/lib/richtext/`), ~150 Zeilen, keine Abhängigkeit. HTML-Rendering nur über den Parser (escaped), Links nur `https://`/`mailto:`. PDF: pdfkit `continued`-Runs mit Font-Wechsel, Listen als Einrückung. Feld `descriptionLong String?` je Position; `description` bleibt einzeilig (E-Rechnung BT-153); `descriptionLong` → BT-154 als Klartext (Markdown-Zeichen entfernt). | §9 „sichere strukturierte Lösung". |
| Drag&Drop / Duplizieren / Produkt inline (4b) | Native HTML5-Drag (`draggable`, `onDragStart/Drop`) ohne Bibliothek; „Position duplizieren"; Produktauswahl mit Suche; „Neues Produkt anlegen" öffnet `<dialog>` mit `ProductForm` (Action `createProductInline`). | keine neuen Abhängigkeiten. |
| Anhänge (4b) | Modell `DocumentAttachment { id, orgId, docType, docId, filename, mime, sizeBytes, sha256, storagePath, uploadedBy, createdAt }`. Ablage auf Platte unter `ATTACHMENTS_DIR` (Default `./data/attachments`, Docker-Volume) als `<orgId>/<sha256>` (dedupliziert, Dateiname nur in DB). Limits: ≤ 10 MB je Datei, ≤ 50 MB je Beleg; Whitelist PDF/PNG/JPG/XML/CSV/TXT/DOCX/XLSX mit **Magic-Byte-Prüfung** für PDF/PNG/JPG/ZIP-basierte; keine ausführbaren Dateien. Zugriff nur über authentifizierte Route `/api/attachments/[id]` (org-geprüft). Im `SendEmailDialog` als Checkbox-Liste neben den Standardanhängen; `sendDocumentEmail` lädt sie vom Speicher. Löschen erlaubt (kein GoBD-Beleg), ChangeLog `ATTACHMENT`/`ADD|REMOVE`. | §38. |
| Abgrenzung | Kein Lager, keine Preislisten, keine Fremdwährungsumrechnung, keine Abschlags-/Teilrechnung (Phase 5), keine PDF-Layout-Optionen (Phase 7). | §60/§58. |

## 3. Tests (§54)

- Rechenwerk: Positionsrabatt Prozent/Fest/beide; Belegrabatt 10 % auf 100 € 19 % + 100 € 7 % → 10 €/10 €, Steuern 17,10 €/6,30 €; Festbetrag 15 € auf 300 €/100 € → 11,25 €/3,75 €; Rundungsrest (3 Sätze, 10 € auf 33,33/33,33/33,34) → Summe exakt 10 €; Aufschlag nach Rabatt; 0 % Satz (Kleinunternehmer/§13b) mit Rabatt; Reverse-Charge unverändert.
- Skonto: Fristen, Betrag, zwei Ziele; Zahlung innerhalb Frist → Vorschlag; außerhalb → kein Vorschlag; Skonto-Payment schließt Rest; ChangeLog.
- E-Rechnung: UBL + CII mit Positions- und Belegrabatt/-aufschlag validieren (`validate:erechnung` erweitert um zwei Fixtures); BT-20 Skonto-Syntax vorhanden; `PaymentMeansCode` aus Methode.
- Zahlungsmethoden: CRUD, Systemschutz, Snapshot beim Festschreiben, `Payment.method` Validierung.
- 4b: Rich-Text-Parser (Escaping, verbotene Links, Listen), Positionsblöcke (Zwischensumme, Ausschluss aus XML), Anhänge (Limits, Magic-Bytes, Org-Zugriff, Dedup, Mailversand mit Anhang).

## 4. Nicht in Phase 4

Teil-/Abschlags-/Schlussrechnung (5), Mahnwesen (6), Nummernkreise/PDF-Layout/GiroCode (7), Dashboard/Timeline (8), MCP-Erweiterungen jenseits der gleichlautenden Validierung (9).
