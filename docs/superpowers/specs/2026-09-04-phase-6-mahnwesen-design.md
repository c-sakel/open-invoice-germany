# Phase 6 — Flexibles Mahnwesen, Scheduler, Mahnübersicht

**Lastenheft:** §23 flexible Mahnstufen, §24 Mahnfristen, §25 Mahnübersicht `/mahnwesen`, §26 Mahn-Automatisierung (eingebauter Scheduler + Cron/API), §27 Teilzahlungen; §54 Testfälle Mahnwesen; Settings-Fragment Mahnwesen (Ruling: in dieser Phase). Bindend §50–§55, §59.
**Ist-Stand:** `phase-6-ist-stand.md` (Erhebung 2026-09-04). Kurz: `DunningStage` (unbegrenzt je Org, unique `[orgId, order]`, 4 Stufen geseedet) und `Dunning` existieren; `createDunning` rechnet den offenen Betrag korrekt (`payableBaseCents − paidAmountCents`), **ignoriert aber die Stufenkonfiguration** (Zinsen/Pauschale hart ab Level 1, `enabled`/`daysAfterDue`/`feeCents` ungenutzt), Stufe = Anzahl bisheriger Mahnungen; keine Übersicht, kein Scheduler, kein Pausieren, kein Auto-Versand, Mahnungen ohne Snapshot, PDF rechnet offenen Betrag ohne `payableBaseCents`, E-Mail-Vorlage wird über Standardnamen statt `stage.emailTemplateId` gewählt, keine Settings-UI.

## 1. Fachliche Klärung (mit Quelle)
- Verzug § 286 BGB; Verzugszinsen § 288 Abs. 1/2 (5 bzw. 9 Prozentpunkte über Basiszins, B2C/B2B); 40-€-Pauschale § 288 Abs. 5 nur B2B, einmal je Forderung (EuGH C-419/21); Mahngebühren nur konkrete Kosten (Porto/Material, BGH VIII ZR 95/18), keine Gebühr auf der ersten Zahlungserinnerung (COMPLIANCE §12). Basiszins halbjährlich (§ 247 BGB) — Pflege als Org-Einstellung mit Gültigkeitsdatum.
- Forderungsbasis = tatsächlich offener Betrag (§27): `payableBaseCents − paidAmountCents` (Phase 5-konform). Zinsen taggenau auf den offenen Betrag ab Fälligkeit+1 bis Mahndatum.
- GoBD: Mahnungen sind aufbewahrungspflichtige Geschäftsbriefe → Snapshot (Verkäufer/Käufer/Beträge) bei Erstellung, ChangeLog `DUNNING CREATE/SEND/STATE`.

## 2. Entscheidungen

| Frage | Entscheidung |
|---|---|
| Stufenmodell | `DunningStage` bleibt; **neu** `autoSend Boolean @default(false)`, `feeCents` nur zulässig bei `order ≥ 2` (Zod + Domain; COMPLIANCE), `documentTemplateId` bleibt als Spalte, wird als „reserviert" dokumentiert (nicht destruktiv). CRUD + Reihenfolge (`order` lückenlos 0..n, Umsortieren = Neuvergabe in einer Tx) + `enabled`. Kein Maximum. Seeds unverändert (4 Stufen). |
| Org-Einstellungen (Settings-Fragment Mahnwesen) | Neues Modell `DunningSettings { orgId @unique, autoCreate Boolean @default(true), autoSend Boolean @default(false), baseInterestRateBp Int @default(127), baseRateValidFrom DateTime?, senderEmailTemplateFallbackId? , gracePeriodDays Int @default(0) }` (Selbstheilung wie MailSettings). `autoSend` je Stufe wirkt nur, wenn global `autoSend` an. |
| Mahnprozess je Rechnung | `Invoice.dunningState String @default("ACTIVE")` ∈ ACTIVE/PAUSED/STOPPED, `dunningPausedUntil DateTime?`, `dunningStateNote String?`. PAUSED mit Datum läuft automatisch aus; STOPPED endgültig (nur manuell zurück auf ACTIVE). Änderung → ChangeLog `INVOICE DUNNING_STATE`. |
| Stufenwahl | Nächste Stufe = erste **enabled** Stufe mit `order > letzte Mahnstufe` (bzw. 0). Fällig ab: Basisdatum + `daysAfterDue`, Basisdatum = Rechnungs-Fälligkeit (Stufe 0) bzw. `dueDate` der letzten Mahnung (neues Zahlungsziel). `nextDunningAt` wird berechnet, nicht gespeichert (Domain `dunningScheduleFor(invoice)`). Manuelles Erzeugen vor Fälligkeit der Stufe erlaubt (Bestätigung im UI), Scheduler nur bei Fälligkeit. |
| Geldlogik | Ausschließlich aus der Stufe: `calculateInterest` → Zinsen (Basiszins aus DunningSettings + 5/9 Pp nach `Customer.type`), `includeB2BFlatFee` → 40 € nur B2B, nur einmal je Rechnung, `feeCents` → Mahnkosten (nur `order ≥ 2`). Snapshot dieser Werte in `Dunning` (bereits vorhanden: `baseInterestRatePermille`→ bleibt, Doku „bp"; neu `claimBaseCents`, `feeCents`). |
| Snapshot | `Dunning.sellerSnapshotJson`, `buyerSnapshotJson`, `claimBaseCents`, `invoiceNumber`, `invoiceDueDate` bei Erstellung; PDF liest ausschließlich Snapshot (Fallback MIGRATION für Altmahnungen per Backfill in der Migration + `ensure`-Selbstheilung). |
| Versand | `sendDunning(id, {actor})` nutzt die Phase-2-E-Mail-Pipeline mit Vorlage aus `stage.emailTemplateId` (Fallback: Standardvorlage `DUNNING` nach Stufenname, letzter Fallback: generische Rechnungsvorlage). `pickDunningTemplate` wird auf `stage.emailTemplateId` umgestellt. `Dunning.sentAt` + EmailLog. Auto-Versand nur bei `settings.autoSend && stage.autoSend`. |
| Scheduler (§26) | Eingebaut: `src/instrumentation.ts` `register()` startet (nur Node-Runtime, `SCHEDULER_ENABLED !== "false"`) einen Intervall-Runner (`SCHEDULER_INTERVAL_MINUTES`, Default 15), der `runScheduledJobs()` aufruft. Jobs seriell (ChangeLog-Unique): `dunning` (neu), `recurring` (bestehend, `runDueRecurring`). Lock per DB (`SchedulerRun { id, job, startedAt, finishedAt?, status RUNNING/OK/FAILED, summaryJson, trigger SCHEDULER/CRON/MANUAL }`, laufender Eintrag < 30 min blockiert); stale locks werden übernommen. Cron/API bleibt: `/api/cron/run-dunning`, `/api/cron/run-all` (CRON_SECRET wie `run-recurring`), Script `npm run dunning:run`. Protokoll in Einstellungen → Automatisierung (letzte 50 Läufe) und „Jetzt ausführen"-Button. |
| Scheduler-Prüfung je Rechnung | Nur Typen INVOICE/CORRECTION/PARTIAL/DOWNPAYMENT/FINAL, Status FINALIZED/SENT/PARTIALLY_PAID (nicht PAID/CANCELLED/DRAFT), offen > 0, `dunningState == ACTIVE` (PAUSED mit abgelaufenem Datum → ACTIVE), kein Storno-Beleg/keine vollständige Gutschrift (offen > 0 deckt das ab), nächste Stufe fällig, `settings.autoCreate`. Keine zweite Mahnung derselben Stufe (Unique `[invoiceId, stageId]`, Altmahnungen ohne stageId unberührt). |
| Übersicht `/mahnwesen` (§25) | Serverseitige Abfrage aller offenen, überfälligen Rechnungen der Org; Widgets: überfällige Anzahl, Gesamt offen, Aging 1–7/8–30/31–60/>60 Tage; Tabelle mit den §25-Spalten (letzte Kontaktaufnahme = letzte EmailLog-Zeit zur Rechnung/Mahnung); Aktionen je Zeile: Zahlung erfassen (bestehendes PaymentForm), Zahlungserinnerung/nächste Mahnung erstellen, Mahnung senden, pausieren (bis Datum), beenden/fortsetzen. Filter Status/Kunde/Stufe. |
| Rechnungsseite | Mahnblock zeigt Prozessstatus, nächste Stufe + Datum, Aktionen wie oben; bestehender `DunningButton` wird ersetzt. |
| Settings-UI | Einstellungen → Mahnwesen: Stufenliste (Name, Tage, neues Ziel, Gebühr, Zinsen, Pauschale, E-Mail-Vorlage, Auto-Versand, aktiv), Hinzufügen/Umsortieren/Deaktivieren/Löschen (Löschen nur ohne verknüpfte Mahnungen, sonst deaktivieren), globale Schalter (autoCreate/autoSend), Basiszins + gültig ab. |
| MCP (§55) | `create_dunning` (bestehend, Stufenlogik), `send_dunning`, `set_dunning_state`, `list_overdue_invoices`, `run_scheduler_job` (job: dunning|recurring; gleiche Domain-Funktion wie Cron). |
| Bugfixes mitnehmen | PDF offener Betrag via Snapshot; `stage.enabled` beachten; Mahnkosten nicht vor 2. Mahnung; Vorlage via `stage.emailTemplateId`; `gobd.test.ts`-Erwartung „stageId null ab Level 4" entfällt (Stufen frei), `phase1.test.ts` Stufenzahl `≥ 4`. |
| Nicht in Phase 6 | Benachrichtigungen (§ „Mahnstufe erreicht", Phase 8/9), Inkasso-Export, Zinsberechnung mit Basiszins-Historie (nur aktueller Satz + gültig-ab; Historie Backlog), Webhooks (10b nutzt den Runner). |
